## 1. 全体アーキテクチャ

```text
[Flutter App] ──(認証)──→ [Cognito] → JWTトークン取得
[Flutter App] ──REST(JWT付き)──→ [API Gateway(トークン検証)] ──→ [Lambda 1つ] ──→ [DynamoDB 6テーブル]
[Flutter App] ──WSS(JWT付き)───→ [API Gateway(トークン検証)] ──→ [Lambda別] ──→ [DynamoDB]
[React Admin] ──REST(JWT付き)──→ [同じAPI Gateway /admin/*]
[S3] = AI生成画像/動画の保存先（初回/更新時に一括DL→スマホローカルに保存、通常時はローカルから読み込み）
```

## 2. 決定事項一覧

| # | 決定事項 | 選択 | 理由 |
|---|---------|------|------|
| 1 | FE構成 | Feature-first + 軽量クリーンアーキテクチャ | 機能単位で分離しつつ開発速度を維持 |
| 2 | BE構成 | Monolithic Lambda + WebSocket専用Lambda | 管理負荷を最小化、WS制約のみ分離 |
| 3 | バトル状態管理 | サーバー側完全管理 | チート防止、整合性保証 |
| 4 | AI画像/動画 | ドット絵スプライトシート方式。事前生成してS3→初回DLでローカル保存。Flameパッケージでアニメーション再生 | レイテンシ回避、ドット絵と高相性、軽量 |
| 5 | リアルタイム通知 | WebSocketはバトル専用 | 実装コスト削減、他はポーリングで十分 |
| 6 | API Gateway | 単一（パスで分離） | ハッカソンで管理が楽 |
| 7 | DB設計 | Table per Entity（6テーブル） | 理解しやすく、テーブル設計が明確 |

**✅ レビュー観点:**
- [ ] 各決定に違和感はないか？
- [ ] 変更したい項目はあるか？

## 3. コンポーネント構成（何を作るか）

### フロントエンド（Flutter アプリ）

| モジュール | やること | 画面イメージ |
|-----------|---------|-------------|
| 認証 | ログイン/サインアップ/プロフィール設定 | ログイン画面、登録画面 |
| 行動記録 | カテゴリ選択→記録、履歴一覧、サマリー | 記録画面、履歴画面 |
| ヘルスデータ | HealthKit/Health Connect連携、起動時同期。スマートウォッチ（Apple Watch, Wear OS等）やスマホの歩数計データはOSのヘルスデータストア経由で間接取得 | 設定画面、起動時サマリー |
| アバター育成 | ぶた表示（ドット絵スプライトアニメーション）、進化演出、ステータス確認 | ホーム画面、アバター詳細 |
| バトル | マッチング、ターン操作、結果表示 | バトル画面 |
| ソーシャル | フレンド管理、SNS共有 | フレンド画面 |

### バックエンド（Lambda）

| コンポーネント | やること |
|--------------|---------|
| REST Lambda（1つ） | 行動記録、アバター管理、ヘルス同期、ソーシャル、管理画面API を全部処理 |
| WebSocket Lambda | バトルのリアルタイム通信だけ |
| Cognito | ログイン認証（メール、Google、X） |

### データベース（DynamoDB 6テーブル）

| テーブル | 保存するもの |
|---------|-------------|
| Users | ユーザー情報（ニックネーム、認証情報、設定） |
| Avatars | ぶたの状態（レベル、ポイント、進化段階、スキル） |
| Records | 不健康行動の記録履歴 |
| Battles | バトルの状態と履歴 |
| Friends | フレンド関係と申請 |
| MasterData | 進化パス定義、スキル定義（管理画面で編集） |

- [ ] 足りないコンポーネントはないか？
- [ ] 不要なコンポーネントはないか？

## 4. データの流れ（主要フロー）

### 不健康行動を記録したとき
```
ユーザーがカテゴリ選択 → REST API → Recording保存 → ポイント計算 → Avatar更新（レベルアップ/進化判定）→ 結果返却
```

### アプリ起動時（ヘルスデータ同期）
```
アプリ起動 → ヘルスデータ取得 → REST API → 基準値と比較 → 不健康行動検出 → ポイント加算 / 健康行動検出 → ポイント減算（退化あり）→ サマリー返却
```

### バトル
```
マッチング申請 → WebSocket接続 → 準備（スキルセット）→ ターンループ（行動選択→サーバー実行→結果配信）→ 終了→ランキング更新
```

**✅ レビュー観点:**
- [ ] フローに抜けや矛盾はないか？
- [ ] ユーザー体験として自然か？

## 5. 気になるポイント（設計者からの補足）

| # | ポイント | 説明 |
|---|---------|------|
| 1 | Monolithic Lambdaのコールドスタート | 全コード読み込みで初回起動が遅くなる可能性。ハッカソン規模では問題なし（対策不要） |
| 2 | バトル中の状態管理 | DynamoDBへの書き込み頻度が高い。ターンごとに状態保存 |
| 3 | 退化メカニクス | 健康行動でポイント減→進化巻き戻し。ユーザーが不快に感じないUX設計が重要 |
| 4 | ドット絵アセットの事前生成量 | 進化パス数 × 段階数 × アニメーション種類（待機/喜び/進化/バトル）のスプライトシートが必要。初期は少数パスでスタート |

- [ ] これらのリスクは許容できるか？
- [ ] 追加で気になるリスクはあるか？
